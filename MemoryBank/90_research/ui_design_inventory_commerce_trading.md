# UI-дизайн: инвентарь, магазины, торговля и обмен

Статус: проект (предложение), 2026-07-26.
Охват: runtime Inventory (личный инвентарь, дарение, обмен, партийное хранилище, force-move) и Commerce (магазины, кошельки, покупка/продажа) во фронтенде `pathfinder.frontend`.

---

## 1. Отправная точка

Backend уже поддерживает все командные сценарии:

- Inventory: `POST /api/campaigns/{campaignId}/inventory/gifts`, `gifts/{key}/accept`, `exchanges`, `exchanges/{key}/complete|cancel`, `party-storage/deposit|withdraw`, `force-move`.
- Commerce (игрок): `POST /api/commerce/campaigns/{campaignId}/purchase-reservations`, `.../cancel`, `.../complete`, `shops/{shopId}/sales`.
- Commerce (ведущий): `POST /api/commerce-admin/campaigns/{campaignId}/wallets/{characterId}/adjustments`, `shops/{shopId}/catalog-offers`, `shops/{shopId}/stock-offers`, `settlements`, `settlements/{id}/shops`, `shops/{shopId}/pricing-policy`.

**Read-проекций нет вообще** — ни одного GET для инвентаря, ассортимента, кошелька, ожидающих подарков или обменов. Это главный блокер UI: раздел 7 фиксирует минимальный контракт чтения, без которого экраны не собрать.

Ключевые особенности модели, которые UI обязан отражать:

- деньги — целые медные (`long *Copper`), кошелёк различает `Balance / Reserved / Available`;
- optimistic concurrency: команды требуют `ExpectedItemVersion` — UI должен уметь показывать конфликт «предмет изменился, обновите»;
- идемпотентность: каждая команда несёт клиентский `OperationId` (GUID) — генерировать на открытии формы, переиспользовать при retry;
- покупка двухфазная: резерв с `ExpiresAtUtc` → complete/cancel;
- обмен строится из линий с резервированием и подтверждается контрагентом;
- offer бывает `Catalog` (порождает новый экземпляр из ревизии каталога) и `Stock` (продаёт физический экземпляр из контейнера магазина).

## 2. Информационная архитектура

Инвентарь и торговля существуют **только в контексте кампании**. Сейчас всё про кампанию свалено в один `CampaignsView` — вводим страницу кампании с вкладками, она станет якорем для новых разделов.

```
/campaigns                                — список кампаний (как сейчас, но карточки-ссылки)
/campaigns/:campaignId                    — страница кампании, вкладки:
    Обзор | Участники | Партия | Хранилище | Торговля
/campaigns/:campaignId/characters/:id     — campaign-карточка персонажа (есть), + вкладка «Инвентарь»
/campaigns/:campaignId/inventory/:id      — инвентарь персонажа (полный экран)
/campaigns/:campaignId/shops/:shopId      — магазин (игрок): Товары | Продажа | Мои резервы
/campaigns/:campaignId/commerce-admin     — панель ведущего: Поселения | Магазины | Кошельки
```

Feature-папки по существующей конвенции: `src/features/inventory/`, `src/features/commerce/` (каждая со своим `api.ts`, логикой с co-located тестами и, при необходимости, `store.ts`).

## 3. Экраны

### 3.1 Инвентарь персонажа

Трёхзонная компоновка (на mobile колонки складываются):

- **Слева (сводка):** карточка кошелька — доступно крупно, резерв и баланс мелко, кнопка «Журнал»; карточка нагрузки — прогресс-бар bulk (норма/перегруз/максимум, `bulkTenths / 10`).
- **Центр:** секции «Экипировано» и «Рюкзак». Строка предмета: иконка категории, название, стопка ×N, bulk, версия не показывается (техническое поле). Меню действий строки: «Подарить», «Предложить обмен», «В хранилище партии», «Продать» (активна, если в кампании есть магазины).
- **Справа (детали):** панель выбранного предмета — данные точной catalog revision: уровень, категория, цена, описание, компоненты (attack/armor/…); provenance (стартовый набор / куплен / подарен) из журнала операций.
- **Верхняя полоса «Входящие»:** ожидающие подарки и активные обмены с бейджами — главная точка входа в подтверждения.

Состояния: скелетон при загрузке; пустой рюкзак — empty-state с подсказкой; конфликт версии при любом действии — tonal-alert «Предмет изменился, список обновлён» + автоматический refetch.

### 3.2 Дарение (диалог, не страница)

Шаги в одном `v-dialog`: предмет уже выбран из строки → выбор получателя (персонажи партии, кроме своего) → подтверждение. После отправки подарок висит в «Исходящие» со статусом «Ожидает подтверждения». У получателя — карточка входящего подарка с «Принять» (и «Отклонить», когда появится команда; до этого — только accept, отклонение = игнор, честно показать это в UI).

### 3.3 Обмен (полноэкранный диалог)

Двухколоночный стол сделки: «Отдаёте» / «Получаете». Каждая сторона добавляет линии из своего инвентаря; линия резервирует предмет (`ReservationOperationId`). Статусная лента: Черновик → Ожидает партнёра → Завершён / Отменён. Правила UI:

- добавление/удаление линий доступно только до отправки;
- контрагент видит предложение целиком и жмёт «Завершить обмен» или «Отклонить»;
- отменить может любая сторона до завершения;
- конфликт версии линии подсвечивает конкретную строку, а не валит весь диалог.

### 3.4 Партийное хранилище (вкладка кампании)

Список предметов с указанием, кто положил и когда (из аудита). Действия: «Взять себе» (withdraw — выбор персонажа, если у игрока их несколько), «Положить» (deposit — выбор из своего инвентаря). Чип политики доступа; для `Unconfigured` — предупреждение и ссылка ведущему на настройку. Внизу — свёрнутый журнал операций хранилища.

### 3.5 Магазин — игрок

Шапка: название магазина, поселение, чип ценовой политики («покупка ×1.0 / скупка ×0.5»). Вкладки:

- **Товары.** Список offer'ов: название, уровень, цена за единицу, наличие (`AvailableQuantity`, для Catalog-офферов может быть «∞» если так настроено), чип «каталог/экземпляр». Кнопка «Купить» → панель резерва: количество, итог, таймер до `ExpiresAtUtc`, «Оплатить» / «Отменить». Недостаток средств блокирует «Оплатить» с объяснением (сравнение с `AvailableCopper`).
- **Продажа.** Инвентарь активного персонажа с расчётной ценой скупки по политике магазина; «Продать» — подтверждение с итогом.
- **Мои резервы.** Активные резервы этого персонажа с таймерами (после истечения — статус Expired, кнопка «Повторить»).

### 3.6 Панель ведущего (commerce-admin)

- **Поселения:** дерево поселение → магазины, создание того и другого.
- **Магазин:** ассортимент (создание catalog-offer через поиск по ItemCatalog и stock-offer из контейнера магазина; смена цены/количества/статуса), форма ценовой политики.
- **Кошельки:** таблица персонажей кампании с балансами, корректировка (`AmountCopper` ±, описание — обязательное поле, попадает в журнал), просмотр журнала кошелька.
- **Инструменты:** force-move предмета (выбор предмета, целевой контейнер, обязательная причина) — с явным предупреждением, что действие аудируется.

## 4. Потоки (happy-path + отказ)

**Покупка:** выбрать оффер → количество → `POST purchase-reservations` (резерв денег, таймер) → «Оплатить» → `complete` → предмет появляется в инвентаре (ссылка «Показать»). Отказ: таймер истёк → резерв освобождён, повторить; недостаточно денег → ошибка до создания резерва.

**Продажа:** предмет → цена по политике → подтверждение → `POST shops/{id}/sales` → деньги в кошельке (снэкбар с суммой).

**Дарение:** предмет → получатель → `POST gifts` → у получателя входящее → `accept` → предмет переехал; версия устарела → пересоздать подарок.

**Обмен:** инициатор собирает линии (каждая с резервом) → `POST exchanges` → контрагент завершает `complete` или любой отменяет `cancel`.

**Хранилище:** deposit/withdraw с `OperationId`; отказ политики доступа — объяснимая ошибка «политика партии запрещает…».

## 5. Общие компоненты (новая папка `src/components/`)

| Компонент | Назначение |
|---|---|
| `MoneyText` | copper → «12 зм 3 см 4 мм» (+ полный формат в tooltip); опция компактности |
| `MoneyInput` | ввод суммы в зм/см/мм, значение — copper |
| `ItemListRow` | строка предмета: иконка категории, имя, стопка, bulk, slot действий |
| `ItemDetailsPanel` | карточка catalog revision предмета |
| `BulkMeter` | прогресс нагрузки с порогами encumbered/max |
| `OperationStatusChip` | Pending / Reserved / Completed / Cancelled / Expired |
| `CountdownChip` | таймер до `ExpiresAtUtc` |
| `AppSnackbarHost` | глобальные снэкбары (сейчас в приложении их нет) |

Форматтер денег: 1 зм = 10 см = 100 мм (платину в отображении пока не используем — бэкенд хранит только copper, конверсия отображения). Локализация: ru «зм/см/мм», en «gp/sp/cp».

## 6. Обновления данных

WebSocket'ов нет. Для входящих подарков/обменов и таймеров резервов — лёгкий polling: `GET pending-операций` раз в 30–60 с на страницах кампании + ручной refresh. Счётчик входящих — бейдж на вкладке кампании и в навигации. Когда появится push-канал — заменить точечно (логика опроса в одном composable `usePendingOperations`).

## 7. Недостающие read-проекции API (блокер)

| Endpoint (предложение) | Что отдаёт |
|---|---|
| `GET /api/campaigns/{cid}/inventory/characters/{id}` | контейнеры, предметы (instanceKey, version, qty, equipped, revision summary), bulk |
| `GET /api/campaigns/{cid}/inventory/party-storage` | содержимое + политика + последние операции аудита |
| `GET /api/campaigns/{cid}/inventory/gifts?role=incoming|outgoing&status=pending` | подарки |
| `GET /api/campaigns/{cid}/inventory/exchanges?participantCharacterId=` | обмены со статусами и линиями |
| `GET /api/commerce/campaigns/{cid}/settlements` | поселения с магазинами |
| `GET /api/commerce/campaigns/{cid}/shops/{shopId}/offers` | активные offer'ы |
| `GET /api/commerce/campaigns/{cid}/shops/{shopId}/sell-quote?itemInstanceKey=` | цена скупки по политике |
| `GET /api/commerce/campaigns/{cid}/wallets/{characterId}` | WalletDto (баланс/резерв/журнал) |
| `GET /api/commerce/campaigns/{cid}/purchase-reservations?buyerCharacterId=&status=active` | резервы |
| `GET /api/item-catalog/revisions?search=&scope=` | поиск по каталогу для admin-offer'ов |

DTO для команд уже возвращаются из POST — их же формы использовать в проекциях, чтобы фронт имел один набор типов.

## 8. Улучшения текущего UI (вне торговли)

1. **Страница кампании с вкладками** вместо монолитного `CampaignsView` — членство/партия/хранилище/торговля перестают тесниться в одной простыне; карточки в `/campaigns` становятся ссылками.
2. **Глобальный snackbar-хост + центр уведомлений** — сейчас ошибки только inline; для асинхронных сценариев (подарок принят, резерв истёк) нужны и снэкбары, и бейджи.
3. **Единый формат денег**: в мастере создания цены показываются сырыми медяками («120 cp») — заменить на `MoneyText` везде, включая шаг Starting Equipment.
4. **Выделить `src/components/`**: CharacterCreateView (2665 строк) и CharacterDetailsView (1186) пора резать; строки предметов/бюджет-алерт из шага 10 переиспользуются инвентарём.
5. **Ленивая загрузка маршрутов** (dynamic import в router) — бандл растёт с каждым большим view.
6. **Бейджи контекста кампании в навигации** — активная кампания и счётчик входящих операций в drawer.
7. Опционально: тёмная тема как вариант `characterLedger` (Vuetify это поддерживает; палитра — те же чернила/пергамент в инверсии).

## 9. Этапность

1. **MVP-1 «посмотреть и передать»:** read-проекции инвентаря/подарков + экран инвентаря + дарение + партийное хранилище.
2. **MVP-2 «магазин»:** проекции commerce + магазин игрока (покупка с резервом, продажа) + кошелёк.
3. **MVP-3 «сделки и админ»:** обмен, панель ведущего, force-move, журнал кошелька.
