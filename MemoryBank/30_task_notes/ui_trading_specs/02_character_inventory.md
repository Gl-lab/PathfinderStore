# ТЗ-02. Инвентарь персонажа

Этап: MVP-1. Мокап: секция 02 в [мокапах](../../90_research/ui_design_inventory_commerce_trading_mockups.html). Сквозные требования — [00_overview_and_shared.md](00_overview_and_shared.md).

## Проблема

Runtime-инвентарь (Inventory bounded context) не имеет никакого UI: игрок не видит свои экземпляры, кошелёк, нагрузку и не может инициировать передачу.

## Цель

Экран инвентаря персонажа в кампании: просмотр экипировки/рюкзака/кошелька/нагрузки, точка входа во все операции передачи (дарение, обмен, хранилище, продажа), полоса входящих операций.

## Маршрут и точки входа

- `/campaigns/:campaignId(\d+)/inventory/:characterId(\d+)`, name `campaign-inventory`.
- Входы: кнопка «Инвентарь» на карточке персонажа во вкладке «Партия» (ТЗ-01) и на campaign-карточке персонажа (`CharacterDetailsView` в campaign mode).
- Доступ: владелец персонажа. GM видит read-only (без меню действий) — серверная авторизация первична.

## Зависимости API

Существующие команды: gifts / exchanges / party-storage / force-move (`PartyInventoryController`).

Требуемые read-проекции (backend-задачи, блокируют):

| Endpoint | Контракт (минимум) |
|---|---|
| `GET /api/campaigns/{cid}/inventory/characters/{characterId}` | `{ containers: [{ containerKey, kind }], items: [{ itemInstanceKey, version, containerKey, quantity, isEquipped, revision: { name, level, primaryCategory, priceInCopperPieces, bulkTenths, description }, provenance?: { kind, occurredAtUtc } }], bulk: { totalTenths, encumberedAtTenths, maximumTenths } }` |
| `GET /api/commerce/campaigns/{cid}/wallets/{characterId}` | существующий `WalletDto` (balance/reserved/available/entries) |
| `GET /api/campaigns/{cid}/inventory/gifts?characterId=&role=incoming\|outgoing&status=pending` | список `PartyGiftDto` |
| `GET /api/campaigns/{cid}/inventory/exchanges?participantCharacterId=&status=pending` | список `PartyExchangeDto` |
| `GET /api/commerce/campaigns/{cid}/settlements` | для активации пункта «Продать» (есть ли магазины) |

## Состав UI

Сетка `230px | 1fr | 260px`, на `< md` — одна колонка (сводка → предметы → детали снизу как bottom sheet/expand).

1. **Шапка:** eyebrow «Кампания {название}», serif «Инвентарь — {имя}», подзаголовок класс/уровень/партия. Справа — полоса «Входящие»: chip с числом ожидающих подарков и обменов (badge из `usePendingOperations`), клик раскрывает список входящих (карточки: подарок → ТЗ-03 accept; обмен → переход в ТЗ-06).
2. **Кошелёк (карточка):** крупно `available` (`MoneyText`), мелкими строками balance и reserved; кнопка «Журнал операций» → диалог со списком `WalletLedgerEntryDto` (дата, вид, сумма ±, остаток, описание). До реализации Commerce-проекций (MVP-2) карточка скрыта фиче-флагом.
3. **Нагрузка (карточка):** `BulkMeter` + текст «X bulk · норма Y · макс Z» (tenths/10, L-предметы по правилам домена уже входят в totalTenths).
4. **Предметы (карточка):** секции «Экипировано» и «Рюкзак» (группировка по `isEquipped`, внутри — по категории, стопки одной строкой `×N`). Строка — `ItemListRow`: иконка категории, имя, стопка, bulk, chip ранга владения (если проекция отдаёт). Клик по строке — выделение + панель деталей. Кнопка `⋮` — меню действий:
   - «Подарить…» → ТЗ-03;
   - «Предложить обмен…» → ТЗ-06 (до MVP-3 пункт скрыт);
   - «В хранилище партии» → deposit из ТЗ-04 (confirm-диалог);
   - «Продать…» → выбор магазина → вкладка «Продажа» ТЗ-05 (до MVP-2 скрыт; при отсутствии магазинов — disabled с подписью «нет магазина»).
5. **Детали (карточка):** имя, чипы (уровень, категория, «ревизия №N»), описание ревизии, цена каталога (`MoneyText`), bulk, происхождение (если есть в проекции). Пусто — подсказка «Выберите предмет».

## Сценарии

1. **Просмотр:** открытие → параллельная загрузка инвентаря, кошелька, pending-операций; скелетоны по зонам независимо.
2. **Выбор предмета:** строка подсвечивается (`bg surface-variant`), панель деталей заполняется. Повторный клик — снятие выбора.
3. **Действие из меню** открывает соответствующий диалог, передавая `itemInstanceKey` + `version`. После успеха — refetch инвентаря + снэкбар.
4. **Конфликт версии** при любом действии — сквозное правило (alert + refetch, диалог остаётся открыт с обновлённой версией, если предмет ещё доступен; иначе диалог закрывается с объяснением).
5. **Входящие:** подарок — «Принять» прямо из раскрытого списка (POST accept + refetch); обмен — переход на экран обмена.
6. **GM read-only:** меню `⋮` и полоса входящих отсутствуют; баннер «Просмотр от лица ведущего».

## Состояния

- Пустой рюкзак: empty-state «Рюкзак пуст. Предметы появятся после назначения кампании или покупки».
- Инвентарь ещё не мигрирован (персонаж не назначен кампании) — сервер вернёт пусто/404: показать объяснение «Инвентарь появится после назначения персонажа в кампанию».
- Ошибка любой зоны — alert с retry в этой зоне, остальные зоны живут.

## Попутно (входит в задачу)

- Реализация общих компонентов из ТЗ-00 (`MoneyText`, `MoneyInput`, `ItemListRow`, `BulkMeter`, `OperationStatusChip`, `CountdownChip`, `AppSnackbarHost`, `useSnackbar`, `usePendingOperations`).
- Замена сырых «NNN cp» на `MoneyText` в шаге Starting Equipment мастера создания и на карточке персонажа.

## Вне охвата

- Перемещение между контейнерами внутри персонажа, экипировка/снятие (нет команд на бэкенде).
- Выбрасывание/уничтожение предметов (нет команды).

## Критерии приёмки

- [ ] Владелец видит все свои экземпляры с корректными стопками, bulk совпадает с проекцией (tenths/10, порог и максимум отражены насечками).
- [ ] Кошелёк показывает available/balance/reserved раздельно; журнал открывается и листается.
- [ ] Каждое действие меню открывает нужный диалог с преднабранным предметом; недоступные действия скрыты/disabled с объяснением.
- [ ] Полоса входящих показывает актуальные счётчики не позже 45 с после появления операции (polling) и мгновенно после ручного refresh.
- [ ] Конфликт версии воспроизводимо обрабатывается (сценарий: два окна, действие во втором, затем в первом).
- [ ] «NNN cp» больше нигде не выводится в мастере создания и карточке персонажа.
- [ ] Общие критерии из ТЗ-00.
