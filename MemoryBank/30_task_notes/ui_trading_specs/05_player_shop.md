# ТЗ-05. Магазин игрока

Этап: MVP-2. Мокап: секция 05. Сквозные требования — [00_overview_and_shared.md](00_overview_and_shared.md).

## Проблема

Commerce поддерживает двухфазную покупку (резерв → оплата) и продажу, UI нет вовсе.

## Цель

Экран магазина: ассортимент с покупкой через резерв, продажа своих предметов по политике скупки, список резервов с таймерами. Плюс листинг магазинов во вкладке «Торговля» (ТЗ-01).

## Маршруты и точки входа

- Вкладка «Торговля» кампании: группировка «Поселение → магазины», карточка магазина → `/campaigns/:campaignId/shops/:shopId` (`campaign-shop`).
- Query `?tab=offers|sell|reservations`, `?characterId=` — активный торгующий персонаж (селектор в шапке; по умолчанию единственный/первый персонаж пользователя в партии).

## Зависимости API

Существующие команды (`CommerceController`): `POST purchase-reservations` (`OperationId, OfferKey, BuyerCharacterId, Quantity`), `.../cancel`, `.../complete`, `POST shops/{shopId}/sales` (`OperationId, SellerCharacterId, ItemInstanceKey`).

Требуемые:

| Endpoint | Контракт (минимум) |
|---|---|
| `GET /api/commerce/campaigns/{cid}/settlements` | `[{ settlementId, name, shops: [{ shopId, name, pricingPolicy: { buyRateBps, sellRateBps } }] }]` |
| `GET .../shops/{shopId}/offers?status=active` | `ShopOfferDto[]` + имя/уровень ревизии (`itemName, itemLevel`) — сырой `ShopOfferDto` содержит только id конфигурации |
| `GET .../wallets/{characterId}` | `WalletDto` |
| `GET .../purchase-reservations?buyerCharacterId=&status=Active\|Expired` | `PurchaseReservationDto[]` + `itemName` |
| `GET .../shops/{shopId}/sell-quote?itemInstanceKey=` | `{ unitPriceCopper }` — цена скупки по политике до подтверждения |

## Состав UI

Шапка: eyebrow «Поселение {название}», serif-название магазина, селектор «торгует: {персонаж}», chip политики «покупка ×{buyRate} · скупка ×{sellRate}». Сетка `1fr | 280px`: слева контент вкладки, справа — панель резерва + мини-кошелёк.

### Вкладка «Товары»

- Список offer'ов (карточка-таблица по стилю проекта, не `v-data-table`): имя, уровень, `MoneyText` цена/ед., наличие (`AvailableQuantity`), chip вида — `каталог` (teal, `Kind=Catalog`) / `экземпляр` (bronze, `Kind=Stock`).
- «Купить»: для каталожного — степпер количества (1..min(наличие, влезает в available деньги)), для экземпляра — количество 1. Кнопка disabled, если `TotalPrice > AvailableCopper`, с warn-alert «не хватает X: доступно Y, в резерве ещё Z».
- Успешный `POST purchase-reservations` → панель резерва справа.

### Панель «Резерв покупки»

Предмет, количество × цена, итого (`MoneyText` крупно), `CountdownChip` до `ExpiresAtUtc`; кнопки «Оплатить» (primary, `complete`) и «Отменить резерв» (outline, `cancel`). Одновременно UI ведёт один активный резерв на панели; остальные — во вкладке «Мои резервы». После `complete`: снэкбар «Куплено: {предмет}» со ссылкой «Показать в инвентаре», refetch offers + wallet.

### Вкладка «Продажа»

Список предметов торгующего персонажа (проекция ТЗ-02), каждый — с ценой скупки из `sell-quote` (ленивая подгрузка по видимым строкам или по клику «Оценить»). «Продать» → confirm-диалог (предмет, цена, «деньги поступят в кошелёк») → `POST sales` → снэкбар «Продано за {сумма}», refetch инвентаря + кошелька.

### Вкладка «Мои резервы»

Список `PurchaseReservationDto` персонажа: предмет, количество, сумма, `OperationStatusChip` + `CountdownChip` для активных. Действия: активный — «Оплатить»/«Отменить»; истёкший — «Повторить» (новый резерв тем же offer/qty, **новый** `OperationId`).

## Сценарии

1. **Покупка:** оффер → количество → резерв (деньги замораживаются: мини-кошелёк показывает рост reserved) → «Оплатить» → предмет в инвентаре.
2. **Истечение резерва:** `CountdownChip` дошёл до нуля → панель помечает резерв «истёк», кнопка «Оплатить» disabled, подпись «Резерв истёк — создайте новый». Авторитетен сервер: если `complete` вернул 400 «expired» — тот же исход.
3. **Отмена резерва:** деньги размораживаются, offer наличие восстанавливается (refetch).
4. **Продажа:** предмет → котировка → confirm → деньги в кошельке.
5. **Конкуренция за stock-offer:** второй покупатель получает 400 «нет наличия» → alert + refetch offers.
6. **Смена торгующего персонажа** обновляет кошелёк, вкладки «Продажа» и «Мои резервы».

## Состояния

- Магазин без активных offer'ов — empty-state «Прилавок пуст».
- Продажа: у предмета нет котировки (магазин не скупает категорию — если политика такое поддерживает) — строка disabled с объяснением.
- Ошибки команд — `getApiErrorMessages` в alert рядом с кнопкой действия.

## Критерии приёмки

- [ ] Полный цикл покупки каталожного offer'а и stock-offer'а: деньги списаны корректно (network: reserved→balance), предмет появился в инвентаре, наличие уменьшилось.
- [ ] Отмена и истечение резерва возвращают деньги (available восстановился) и наличие.
- [ ] Продажа зачисляет сумму, равную котировке; предмет исчез из инвентаря.
- [ ] Недостаток средств блокирует покупку до запроса, с точным объяснением сумм.
- [ ] «Повторить» для истёкшего резерва создаёт новый с новым `OperationId` (проверка в network-логе).
- [ ] Таймеры не расходятся с сервером более чем на визуальную погрешность: по истечении UI не даёт «Оплатить», а серверный отказ обработан идентично.
- [ ] Общие критерии из ТЗ-00.
