# ТЗ-06. Стол обмена

Этап: MVP-3. Мокап: секция 04. Сквозные требования — [00_overview_and_shared.md](00_overview_and_shared.md).

## Проблема

Домен реализует атомарный резервируемый обмен между персонажами; UI нет.

## Цель

Экран сделки: инициатор собирает предложение из линий обеих сторон, контрагент подтверждает, любой может отменить.

## Модель взаимодействия (важно)

По контракту `CreatePartyExchangeCommand` инициатор отправляет **все** линии сразу (`FromCharacterId` в каждой), т.е. черновик собирается локально у инициатора, включая предметы контрагента. Резервирование происходит в момент `POST exchanges` (каждая линия несёт `ReservationOperationId`). Следствия для UI:

- этап «Черновик» — чисто клиентское состояние, без запросов;
- инициатору нужен просмотр инвентаря контрагента (read-проекция должна разрешать участникам партии видеть предметы друг друга минимум в объёме имя/количество/bulk — **зафиксировать в backend-задаче проекции ТЗ-02**);
- после `POST` состав заморожен; «переговоры» = отмена и новая сделка.

## Маршруты и точки входа

- `/campaigns/:campaignId/exchanges/:exchangeKey` (`campaign-exchange`) — просмотр/подтверждение существующей сделки.
- Создание: «Предложить обмен…» из меню предмета (ТЗ-02) → полноэкранный диалог создания (без URL до отправки); предмет преднабран в «Вы отдаёте».
- Входы контрагента: полоса «Входящие» инвентаря, счётчик вкладки кампании.

## Зависимости API

Существующие: `POST exchanges`, `POST exchanges/{key}/complete|cancel` (`OperationId`).

Требуемые: `GET .../inventory/exchanges?participantCharacterId=&status=` и `GET .../inventory/exchanges/{exchangeKey}` (статус, стороны, линии с именами предметов); проекция инвентаря членов партии (см. выше).

## Состав UI

### Создание (инициатор)

- Шапка: «Обмен предметами», «{мой персонаж} ⇄ {контрагент ▾}» (select персонажей партии).
- Две карточки-колонки: **«Вы отдаёте»** (предметы моего персонажа) и **«Вы получаете»** (предметы контрагента). В каждой: строки-линии (`ItemListRow` + кнопка ✕) и «+ Добавить предмет» → диалог-выбор из соответствующего инвентаря (для стопок — количество, если команда поддерживает частичную стопку — тот же открытый вопрос, что в ТЗ-03).
- Допустима односторонняя сделка (линии только с одной стороны) — по сути подарок с подтверждением; UI не запрещает, но подсказывает «Контрагент ничего не отдаёт».
- Кнопки: «Отправить предложение» (primary, disabled при 0 линий), «Отмена».
- `ExchangeKey` и `ReservationOperationId` линий генерируются при открытии.

### Просмотр (оба участника)

- Статусная лента: Черновик → Ожидает партнёра → Завершён / Отменён (текущий выделен).
- Те же две колонки read-only, ракурс зрителя: для контрагента колонки меняются местами (его «Вы отдаёте» — его предметы). Линии с chip `резерв`.
- Действия по ролям: контрагент — «Завершить обмен» (primary) и «Отклонить» (= cancel, danger); инициатор — «Отменить сделку» (danger) и заблокированная primary с подписью «жмёт партнёр».

## Сценарии

1. **Успех:** инициатор собрал 2+2 линии → отправил (200: резервы встали, у обоих предметы chip `в сделке`) → контрагент открыл из «Входящих» → «Завершить» → 200: атомарный перенос, снэкбары обоим при следующем poll/refetch.
2. **Отмена:** любой участник → confirm → резервы сняты, предметы разблокированы.
3. **Конфликт версии при создании:** 400 указывает линию → alert подсвечивает конкретную строку («{предмет} изменился — строка снята»), строка помечается error, кнопка «Отправить» снова активна после исправления. Остальные строки не трогаются.
4. **Конфликт/недоступность при complete:** 400 → alert «Сделка не может быть завершена: {причина}»; предлагаемое действие — «Отменить сделку».
5. **Двойной complete/cancel** (оба окна) — идемпотентный `OperationId`, второй ответ не создаёт дублей; UI показывает финальный статус.

## Состояния

- Список моих сделок (входящие/исходящие pending) — внутри полосы «Входящие» ТЗ-02; отдельного экрана-списка не делаем.
- Завершённая/отменённая сделка по прямому URL — read-only с финальным статусом.

## Критерии приёмки

- [ ] Полный цикл двумя пользователями: создание → резерв виден у обоих → complete → предметы атомарно поменяли владельцев.
- [ ] Отмена с любой стороны снимает резервы у обеих сторон.
- [ ] Конфликт версии подсвечивает конкретную линию, не сбрасывая остальной черновик.
- [ ] У инициатора нет активной кнопки завершения; у контрагента есть; ракурс колонок корректен для обоих.
- [ ] Зарезервированные предметы недоступны для дарения/продажи/хранилища из UI.
- [ ] Общие критерии из ТЗ-00.
