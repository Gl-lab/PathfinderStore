# ТЗ-03. Дарение предмета

Этап: MVP-1. Мокап: секция 03 (левая колонка). Сквозные требования — [00_overview_and_shared.md](00_overview_and_shared.md).

## Проблема

Домен поддерживает подтверждаемое дарение (`gifts` + `accept`), UI отсутствует.

## Цель

Диалог отправки подарка из инвентаря + карточки входящих/исходящих подарков с принятием получателем.

## Точки входа

- «Подарить…» в меню строки предмета (ТЗ-02) — предмет преднабран.
- Входящий подарок: полоса «Входящие» инвентаря (ТЗ-02) и счётчик на вкладке кампании (ТЗ-01).

## Зависимости API

Существующие: `POST /api/campaigns/{cid}/inventory/gifts` (`GiftKey, SourceCharacterId, DestinationCharacterId, ItemInstanceKey, ExpectedItemVersion`), `POST .../gifts/{giftKey}/accept` (`OperationId`).

Требуемые:

| Endpoint | Назначение |
|---|---|
| `GET .../inventory/gifts?...` (из ТЗ-02) | списки входящих/исходящих pending |
| Существующие GET партий (`/api/campaign-parties/...`) | список персонажей-получателей |

Открытый вопрос backend: команды «отклонить подарок» нет — UI не рисует фиктивную кнопку. Если появится `reject`, добавить симметрично accept (отдельная задача).

## Состав UI

### Диалог «Подарить предмет» (`v-dialog`, ~480px)

1. Строка предмета (read-only): `ItemListRow` без действий. Для стопки — поле «Количество» (1..N в стопке), если backend поддерживает частичное дарение стопки; **открытый вопрос** — если команда переносит только целый экземпляр/стопку, поле не показывается.
2. `v-select` «Получатель»: персонажи активной партии кампании, кроме персонажей текущего пользователя; элемент — аватар + имя + игрок. Пустой список → диалог заменяется подсказкой «В партии нет других персонажей».
3. Info-alert: «Подарок вступит в силу после подтверждения получателем. До этого предмет заблокирован от других операций».
4. Кнопки: «Отмена» (text) / «Отправить» (primary, disabled пока получатель не выбран).

`GiftKey` генерируется при открытии диалога; повтор «Отправить» после сетевой ошибки шлёт тот же ключ.

### Карточка входящего подарка

`v-card`: иконка+имя предмета, «от {персонаж}», давность, chip `ожидает`; кнопки «Принять» (primary) и «Позже» (text — просто сворачивает). Accept шлёт `OperationId` (генерится при первом показе карточки и переиспользуется).

### Исходящие

Блок «Исходящие» в раскрытой полосе «Входящие» (общий popover): предмет → получатель, chip `ожидает`, без действий (отмены подарка в API нет — **открытый вопрос**, при появлении добавить «Отозвать»).

## Сценарии

1. **Отправка:** меню → диалог → получатель → «Отправить» → 200: снэкбар «Подарок отправлен {имя}», предмет в списке помечается chip `в подарке` (блокирован), refetch инвентаря.
2. **Принятие:** карточка → «Принять» → 200: снэкбар «Получено: {предмет}», предмет появляется в инвентаре получателя, счётчики обновляются.
3. **Конфликт версии при отправке:** сквозное правило; если предмет исчез (продан/передан) — диалог закрывается с alert-объяснением.
4. **Подарок уже принят/недействителен при accept:** 400 от сервера → карточка помечается «недоступен», исчезает при следующем refetch.
5. **Сетевая ошибка:** кнопка возвращается в активное состояние, повтор с тем же ключом (идемпотентность).

## Состояния

- Отправка/принятие — loading на кнопке (`v-btn :loading`), диалог не закрывается до ответа.
- Ошибки бизнес-правил (запрет передачи предмета доменной политикой) — текст из `getApiErrorMessages` внутри диалога.

## Критерии приёмки

- [ ] Полный цикл на двух пользователях: отправил → у получателя появился (≤45 с или по refresh) → принял → предмет переехал, у отправителя пропал.
- [ ] Подаренный-но-не-принятый предмет визуально заблокирован у отправителя и недоступен для других операций из UI.
- [ ] Двойной клик «Отправить»/«Принять» не создаёт дублей (идемпотентность подтверждена в network-логе: один и тот же ключ).
- [ ] Нет кнопок без команды на бэкенде («Отклонить»/«Отозвать» отсутствуют).
- [ ] Общие критерии из ТЗ-00.
