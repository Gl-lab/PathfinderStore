# ТЗ: подсказки для заблокированных действий и прозрачность шагов UI

Дата ревью: 2026-07-26/27.
Метод: статический аудит всех `.vue`-компонентов `pathfinder.frontend/src` + живой прогон на локальном стенде (backend + PostgreSQL + Vite dev server, пользователь `admin`). Живьём пройдены: логин, дашборд, мастер создания персонажа (шаги 1–8, класс Жрец), список кампаний, новая страница деталей кампании с вкладками.

**Статус:** П1–П10 выполнены 27 июля 2026 года; результат и общий quality gate зафиксированы в [итоговом cross-review Priority 19](priority_19_final_review.md).

Важно: параллельно с ревью в working tree шла активная разработка (вкладки деталей кампании, `MoneyText`, inventory/commerce views). Номера строк ниже даны по состоянию на момент аудита и могут смещаться — ориентироваться на якоря (имена компонентов, computed, i18n-ключи).

## 3. Задачи на исправление

### П1 (высокий). Причина блокировки «Далее» на каждом шаге мастера

**Статус:** выполнено.

**Проблема.** На 10 из 11 шагов кнопка «Далее» просто серая. Пользователь, закрывший шаг наполовину (например, выбрал наследие, но не талант; выбрал доктрину, но не божество), не видит, что именно осталось.

**Что сделать.**
- Ввести общий механизм: для каждого шага computed-список незакрытых требований (строки для UI), по образцу `witchSpellLoadoutRequirements`.
- Пока список непуст: показывать под контентом шага компактный блок «Чтобы продолжить: …» (v-alert tonal warning) и связывать его с кнопкой через `aria-describedby`.
- Показ блока можно смягчить: появлять после первой попытки нажать заблокированную кнопку или после взаимодействия с шагом, чтобы не ругаться на нетронутую форму. Клик по заблокированной зоне: Vuetify-кнопка с `disabled` не ловит события — если нужен обработчик «клик по серой кнопке», оборачивать её в span/div.
- Минимальный состав требований по шагам: 1 — имя, пол, корректный возраст; 3 — наследие, талант; 4 — счётчик бустов; 5 — буст предыстории, свободный буст, выборы обучения; 6 — перечень классовых выборов (доктрина/божество/купель/домен/освящение/муза/патрон и т.д. по классу); 7 — счётчики чар/слотов по классам; 8 — бусты + языки; 9 — навыки; 10 — снаряжение.

**Критерий приёмки.** На любом шаге при заблокированной «Далее» на экране есть текст, перечисляющий конкретные незакрытые пункты; скринридер получает его через `aria-describedby`.

### П2 (высокий). Подсказки у форм кампаний

**Статус:** выполнено.

**Проблема.** «Создать кампанию», «Пригласить», «Создать группу», «Добавить персонажа» блокируются молча. Учитывать, что UI переезжает в новую страницу деталей кампании с вкладками — исправлять уже в ней.

**Что сделать.**
- Полям добавить `:rules`/`hint` («Введите название кампании (до 200 символов)», «Укажите никнейм или e-mail участника»), чтобы причина была видна до и во время ввода.
- Либо не блокировать кнопку, а валидировать при сабмите с показом ошибки поля — единый подход выбрать и зафиксировать (см. П8).

**Критерий приёмки.** Для каждой из четырёх кнопок: пустое/невалидное поле → на экране текст, что требуется; после исправления кнопка активна.

### П3 (средний). Счётчики выбора там, где есть лимит

**Статус:** выполнено.

**Проблема.** Шаг 4: «Выберите 2: разные характеристики» — без счётчика; при достижении лимита остальные чекбоксы блокируются без объяснения. Шаг 7: «Выберите 5 разных чар…» — прогресса не видно. (Шаг 8 уже сделан правильно.)

**Что сделать.** Добавить в hint живой счётчик «Выбрано: N из M» (i18n-паттерн как `wizard.finalFreeBoostsHint`); формулировку шага 4 «Выберите 2: разные характеристики» заменить на человеческую («Выберите 2 разные характеристики. Выбрано: N из 2»).

**Критерий приёмки.** На шагах 4 и 7 виден текущий прогресс выбора; текст согласован грамматически.

### П4 (средний). Обязательные поля шага 1 не помечены

**Статус:** выполнено.

**Проблема.** «Имя персонажа» и «Пол» обязательны (гейтят «Далее»), «Краткая концепция» и «Возраст» — нет, визуально они неотличимы.

**Что сделать.** Пометить обязательные поля (звёздочка/`required` у v-text-field и radio-group label) или подписать необязательные («необязательно»). Единый стиль на все формы приложения.

**Критерий приёмки.** На шаге 1 видно, какие поля обязательны; тот же приём применён к формам кампаний и auth.

### П5 (средний). Сырые идентификаторы и англоязычные строки в русском UI

**Статус:** выполнено.

**Проблема (видно живьём на шаге 6, Жрец).**
- Сырые ID: «Домены: domain.cities, domain.earth, domain.travel, domain.wealth».
- Английские значения в селектах и текстах: Cloistered Cleric / Warpriest, Abadar, Cities/Earth/Travel/Wealth, Society, Crossbow, названия заклинаний, «Grants training in Religion.», блоки Additional Skills / Spellcasting / Deity / Doctrine, «Perception — обучен» (полурусские строки).
- Шаг 5: обучение предыстории — Religion / Scribing Lore / Student of the Canon с английскими описаниями.

**Что сделать.** Провести инвентаризацию таких строк (грепом по шаблону `[a-z]+\.[a-z_]+` в отображаемых данных и по английским текстам с сервера); для доменов/божеств/навыков/оружия/заклинаний выводить локализованные названия (или honest-плейсхолдер), сырые ID не показывать никогда. Решить стратегию: локализация каталога на сервере или словарь на клиенте.

**Критерий приёмки.** На шагах 5–7 при выборе Жреца/Ведьмы/Волшебника нет строк вида `domain.*` и непереведённых служебных описаний; названия в селектах — на языке интерфейса (для терминов правил допускается принятое решение «оставляем англ. термины», но оно должно быть единым).

### П6 (средний). Служебные заметки разработчика в UI

**Статус:** выполнено.

**Проблема.** Пользователь видит: «Талант будет применён после добавления подсистемы талантов», «Домены и дарованные заклинания пока отображаются декларативно», «Grants Domain Initiate and requires a domain choice».

**Что сделать.** Убрать/переформулировать в пользовательские тексты («Талант появится на листе персонажа позже» — если вообще нужно), либо скрыть за feature-флагом. Прогрепать i18n на подобные заметки.

**Критерий приёмки.** В мастере нет текстов о внутреннем устройстве/планах разработки.

### П7 (средний). Перегруженность шага 6 «Класс»

**Статус:** выполнено.

**Проблема.** Для Жреца на одном экране: селект класса, HP, доктрина, божество, купель, домен, освящение, длинная справка о божестве (со сырыми ID), ключевая характеристика, список тренировок (Восприятие/Спасброски/Атаки/Защита/КС класса), Additional Skills/Spellcasting/Deity/Doctrine. Выборы перемешаны со справкой, обязательное не отделено от информационного.

**Что сделать.**
- Визуально разделить: сверху блок «Ваши выборы» (селекты/радио), ниже сворачиваемая справка (v-expansion-panel «Что даёт класс»).
- Справку о божестве показывать компактно после выбора, без перечисления всех доменов текстом.
- Порядок выборов сверху вниз = порядок обязательности; вместе с П1 блок «Чтобы продолжить» замыкает картину.

**Критерий приёмки.** На шаге 6 интерактивные выборы визуально сгруппированы и отделены от справочной информации; экран проходит проверку «пользователь за 5 секунд понимает, что от него требуется».

### П8 (низкий). Живая валидация Login/Register

**Статус:** выполнено.

**Проблема.** Кнопки сабмита всегда активны, ошибки — только серверные после запроса; несовпадение паролей выясняется после сабмита.

**Что сделать.** Добавить `:rules` на поля (required, совпадение паролей), ошибки показывать по blur/submit у поля. Кнопку не блокировать (паттерн «активная кнопка + подсветка ошибок» здесь уместнее серого сабмита).

**Критерий приёмки.** Несовпадающие пароли подсвечиваются до запроса на сервер; пустые поля дают понятные сообщения у самих полей.

### П9 (низкий). Потеря прогресса мастера

**Статус:** выполнено.

**Проблема.** Любая перезагрузка страницы сбрасывает мастер на шаг 1 без предупреждения (воспроизведено дважды). 11 шагов — дорогая потеря.

**Что сделать (по возрастанию стоимости).** 1) `beforeunload`-предупреждение при заполненном черновике; 2) сохранение черновика формы в sessionStorage и восстановление; 3) серверные черновики (уже есть DraftCharacter — вне рамок этого ТЗ).

**Критерий приёмки.** Случайный F5/закрытие вкладки не уничтожает молча заполненный наполовину мастер.

### П10 (низкий). Подтверждение необратимых действий кампании

**Статус:** выполнено.

**Проблема.** «Архивировать», «Снять роль ведущего», «Выйти» (из кампании) срабатывают в один клик (у удаления персонажа confirm-диалог есть — использовать его как образец). Снятие роли с единственного ведущего требует отдельной защиты или объяснения последствий.

**Что сделать.** Confirm-диалог с описанием последствий для всех трёх действий; для «Снять роль ведущего» у единственного ведущего — блокировка с объяснением или явное предупреждение.

**Критерий приёмки.** Ни одно из действий не выполняется без явного подтверждения; попытка снять роль единственного ведущего объясняет последствия.

## 4. Общие правила (Definition of Done для всего ТЗ)

1. Любая заблокированная CTA-кнопка сопровождается видимым текстом причины (постоянный hint, alert-чек-лист или валидационное сообщение поля) — «серых кнопок без объяснения» не остаётся.
2. Объяснение доступно и скринридеру (`aria-describedby` или текст в потоке до кнопки).
3. Не полагаться на tooltip-по-hover у disabled-кнопок: Vuetify не пробрасывает события на disabled, мобильных hover нет. Tooltip — только как дополнение.
4. Все новые строки — через i18n (`src/i18n`), без хардкода в шаблонах.
5. Новые экраны (детали кампании, хранилище, торговля) с первого коммита следуют этим правилам; плейсхолдеры вкладок («…появится на этой вкладке») — приемлемый паттерн.

## 5. Наблюдения вне рамок ТЗ (зафиксировать, решить отдельно)

- При переключении вкладок деталей кампании контент соседних вкладок какое-то время виден одновременно (стекается вертикально) — проверить `v-window`/`v-tabs` разметку новой страницы после завершения текущей разработки.
- Шаг 5: выбор предыстории — селект без описаний предысторий; выбор «вслепую» (названия без пояснений). Аналогично таланты шага 3. Кандидат на карточки/описания при выборе.
- Хинт шага 1 дословно дублирует подзаголовок страницы — заменить на инструкцию по заполнению шага.
